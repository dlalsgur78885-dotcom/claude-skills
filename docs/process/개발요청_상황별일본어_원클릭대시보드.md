어느 쪽이 맞는지 알 수 없어진다 — 실제로 파일명이 갈라져 규칙이 두 벌로 쌓인 적이 있다.

## 화면 흐름

**모두 한 페이지에서 보인다. 페이지 이동은 없다** (2026-09-02 사람 확인 — 「1단계가 한페이지로 클릭하면 2~6단계가 한 페이지에 나와야 해」).

주소는 **하나**다. 예: `/studio/ja-situations`

- 1단계에서 주제를 고르면 **그 아래로** 2단계 블록이 이어서 열리고, 3·4·5·6도 같은 식으로 내려간다.
- **새 주소로 넘기거나 새 탭을 열지 않는다.** 단계마다 화면이 바뀜어 앞 단계가 안 보이게 하지 마라 —
  고른 주제·훅·사진을 위로 올려 다시 보면서 다음을 고를 수 있어야 한다.
- 끝난 단계는 고른 값만 접어서 보여줘도 된다. 다만 **다시 펼쳐 고칠 수 있게** 한다.
- 밖으로 나가는 주소는 **마지막 6단계의 편집 링크(`/editor/{id}`) 하나뿐**이다.

| # | 화면이 하는 일 | 사람이 하는 조작 |
|---|---|---|
| 1 | 주제 후보 **10개** 생성 (이력에 있는 주제는 빼고) | 후보마다 **[보관] [삭제]**, 그리고 하나 **선택** |
| 2 | 훅 문구 후보 **3줄 5개 + 2줄 5개** | **택 1** — 고른 줄 수가 표지 낱장(`표지_3줄`/`표지_2줄`)을 정한다 |
| 3 | 썸네일 이미지 **인물 5장 + 풍경 5장** 생성 | **택 1** — 그 1장이 표지·CTA 배경에 같이 들어간다 |
| 4 | 본문 **10개** 생성 (일본어 / 읽는 방법 / 의미 / 사용 가능한 상황) | 빼고 싶은 것 **제외 체크** |
| 5 | 캡션 문구 1안 | **[재생성] [확인]** |
| 6 | [확인] 누르면 캐러셀 생성 → **편집 링크** 표시 | 링크를 눌러 스튜디오에서 낱장 손보기 |

- 1·2·4단계는 **네 칸·줄 수·글자 수 형식이 지침서에 박혀 있다.** 화면 표도 그 형식 그대로 보여준다.
  (본문은 항목마다 네 줄 세로, 의미는 큰따옴표 포함, 사용 상황은 두 줄)
- 중간에 새로고침해도 고른 것이 날아가지 않게 회차 상태를 서버에 남겨 주면 좋겠다.
  안 되면 필수는 아니다 — 한 자리에서 끝나는 흐름이라.

## 없는 것 — **이미지 생성 엔드포인트** (3단계가 여기서 막힌다)

`backend/app/api/images.py` 에는 `upload · proxy · search · restyle · enhance · cutout` 뿐이고
**그림을 새로 그리는 경로가 없다.** 봇의 `generate_image` 는 Codex CLI 내장 기능이라 서버가 부를 수 없다.

3단계(인물 5 + 풍경 5)를 화면에서 누르게 하려면 **서버에 이미지 생성 경로를 하나 새로 내야 한다.**
`codex-sol` 을 붙일 때 쓴 `_call_codex_cli()` 와 같은 방식(CLI 호출 + 결과 파일 회수 + `uploads/` 로 저장)이면 될 것 같은데,
**실제로 되는지는 개발 쪽에서 확인해 주십시오.** 한 번에 5장, 세로 `1024x1536` 이 기본이다.

- 안 되면 3단계만 지금처럼 봇에 맡기고, 화면은 **이미지 URL 을 붙여넣는 칸**으로 두는 것도 방법이다.
  그 경우 나머지 다섯 단계는 화면에서 그대로 돈다.

## 문구 생성에서 지켜야 할 것

- **모든 문구는 `codex sol`(`codex-sol`) 이 짓는다** — 주제 후보·훅·본문·캡션 전부.
  (→ [개발요청_문구생성모델_codexsol.md](개발요청_문구생성모델_codexsol.md))
- 프롬프트에는 **그 단계 지침서 파일의 규칙을 함께 실어야 한다.** 개수·줄 수·글자 수·형식·톤을 안 적으면 쓸 수 없는 것이 나온다.
- 1단계는 프롬프트에 **[제작 이력](상황별일본어_이력.md) 목록을 함께 넣어** 이미 만든 주제를 빼게 한다.
- 6단계에서 캐러셀을 만들면 **이력에 `날짜 · 주제 · 캐러셀 id` 한 줄이 자동으로 붙어야** 한다.
  지금은 봇이 손으로 적는다. 화면이 대신 적어 주면 다음 회차 1단계가 그대로 읽는다.

## 6단계에서 지켜야 할 것 — 세 인자는 반드시 함께

[4단계 지침서](상황별일본어_4단계_편집링크.md) 의 규칙을 그대로 따른다. 하나라도 빠지면 조용히 망가진다.

| 인자 | 안 넘기면 |
|---|---|
| `slides` | 서버가 문구를 **새로 지어낸다** — 확정 본문이 사라진다 |
| `layout_overrides` | **전부 표지로 렌더된다** (한글 낱장 이름이 영문 키에 안 걸려 첫 낱장으로 떨어진다) |
| `user_image_urls` | 표지·CTA **배경이 빈 채로** 나온다 |

- 템플릿은 **트래블뷰 (id 80)** 고정.
- 낱장: `0` 표지_2줄|표지_3줄 · `1~N` `본문(상황일본어)` · 마지막 `CTA`.
- 본문 네 칸 매핑: 일본어→`headline` / 읽는 방법→`subtext` / 의미→`body` / 사용 가능한 상황→`tag`.
  **줄바꿈·큰따옴표까지 글자 그대로** 넘긴다. 화면에서 다듬지 않는다.

## 확인이 필요한 것

1. **캡션과 편집 링크의 순서가 지침서와 반대다.**
   지시하신 화면 순서는 5 캡션 → 6 편집 링크인데, 지침서는 4 편집 링크 → 5 캡션이다.
   화면만 순서를 바꾸고 **파일 이름·단계 번호는 그대로 두는 것**으로 이해하고 적었다.
   (캐러셀을 먼저 만들어야 캡션에 링크를 걸 수 있고, 지금 5단계 문서도 캐러셀 id 를 함께 적는다.)
   다르게 원하시면 알려 주십시오.

보관·삭제는 확인됐다 — 아래 절 참고.

## 1단계 [보관]·[삭제] — 확정 (2026-09-02 사람 확인)

- **[보관] = 그대로 남겨 둔다.** 이번 회차에 안 쓸 뿐 버리지 않고, **다음 회차에 다시 나온다.**
  → 이력 파일과는 별개인 **보관함 목록**이 필요하다. 이력은 「실제로 만든 주제」만 쌓는 자리라 섞으면 안 된다.
  다음 회차 1단계는 보관한 주제를 먼저 보여 주고, 새 후보는 그것과 겹치지 않게 뽑는다.
- **[삭제] = 이번 목록에서 빼는 것이다. 영구 봉인이 아니다.**
  1단계 지침서가 「안 고른 후보는 이력에 적지 않는다 — 만들지 않은 주제는 다시 나와도 되고,
  좋은 후보를 영구히 봉인하는 쪽이 더 아깝다」고 박아 두었다. 그 규칙을 그대로 따른다.
- **다시 안 나오게 막는 것은 이력뿐이고, 이력에는 6단계에서 실제로 캐러셀을 만든 주제만 올라간다.**

## 개발 답변 (2026-09-02)

### ① 이미지 생성 — **된다.** 다만 두 가지를 알고 설계해야 한다

서버(백엔드와 같은 파이썬 asyncio)에서 codex CLI 를 띄워 **실제로 만들어 봤다.**
세로 1024x1536 두 장 모두 성공(2.4MB · 3.0MB). 방식은 짐작하신 그대로다.

- ⚠ **결과 파일은 「요청한 자리」에 없다.** 두 장 다 codex 자기 폴더
  (`~/.codex/generated_images/<thread_id>/`)에서 회수해야 했다. codex 는 그림을 자기 폴더에
  먼저 넣고 요청 위치로는 **셸 명령으로 옮기는데**, 윈도우 샌드박스가 그 셸을 막는다.
  봇의 `src/codex-image.js` 가 겪은 것과 같은 함정이라 회수 코드를 그대로 쓰면 된다.
- ⚠ **느리다.** 두 장을 **동시에** 돌려 108초 / 224초였다. 10장(인물5+풍경5)이면 몇 분이다.
  → **웹 요청 하나로 기다리게 하면 안 된다.** 만들기를 시작시키고 진행 상태를 따로 물어보는
  방식(백그라운드 작업 + 폴링)이어야 한다. 3단계 화면에는 진행 표시가 필요하다.

### ② ⚠ 먼저 정해야 할 것 — **이 화면을 어디서 돌릴 것인가**

이게 제일 큰 갈림길이라 위 두 가지보다 먼저다.

`codex login status` = **`Logged in using ChatGPT`** 다. 지금 codex 는 **이 PC 의 구독 로그인**에
묶여 있다 — 그래서 API 키 없이 공짜로 쓰고 있는 것이다.
**prod 서버(3.35.18.166)에는 codex 가 설치돼 있지 않고 로그인 세션도 없다.**
그대로 올리면 문구는 예전 모델(gemini-flash)로 되돌아가고, 이미지 생성은 아예 안 된다.

| 길 | 뜻 | 비용 |
|---|---|---|
| (A) 이 PC 에서 화면을 돌린다 | 지금 봇이 도는 방식 그대로. codex 가 바로 된다 | 없음(구독) |
| (B) prod 에 올리고 `codex login --with-api-key` | OpenAI API 키를 서버에 넣는다 | **종량 과금으로 바뀐다** |

(A) 는 PC 가 켜져 있어야 접속된다. (B) 는 어디서나 되지만 돈이 나간다.
**사람이 골라 주셔야 그 다음이 정해진다.**

### ③ 캡션(5)과 편집 링크(6) 순서 — **지시하신 화면 순서대로 해도 된다**

걱정하신 「캐러셀을 먼저 만들어야 캡션에 링크를 걸 수 있다」는 실제로는 문제가 안 된다.
5단계 문서를 확인해 보니 **캡션 본문에 링크가 들어가지 않는다.** 링크 이야기는
「링크를 보내는 그 메시지에 캡션 만들지 물어라」는 **대화 순서 규칙**이고, 화면에는 메시지가
없으니 해당되지 않는다.

즉 데이터 의존이 없다 → **5 캡션 → 6 편집 링크 그대로 가면 된다.**
적어 두신 「화면만 그 순서, 파일 번호는 그대로」도 맞다.

### 남은 판단

②의 (A)/(B) 만 정해 주시면 된다. 나머지는 이 문서대로 만들 수 있다.

### 바라는 모습

1단계 블록을 세 덩이로 나눈다.

| 덩이 | 내용 | 규칙 |
|---|---|---|
| 작업중 | 아직 6단계까지 안 간 내 회차 — 주제 · 지금 단계 · 마지막 시각 | 누르면 **그 회차를 이어서** 연다. [주제 생성] 을 눌러도 안 사라진다 |

## 추가 요청 — 보관 주제는 **미리 다 만들어** 둔다 (2026-09-03)

요청자: solhee 방 · 2026-09-03 · 위 「작업중·보관 고정」 절에 이어지는 요청

### 사람 지시 그대로

> 보관한 주제는 클릭했을 때 생성하지말고 미리 다 생성이 되어있도록, 사용자가 기다리지 않고 선택만 하도록 해줘

범위를 되물었고(문구만 / 사진까지), 답은 **「전부」** 였다. 사진 선생성의 부담(주제 하나당 20~40분)을
알려드린 뒤의 결정이다.

### 바라는 모습

주제를 **[보관]** 하는 순간부터 뒤에서 미리 지어 둔다. 나중에 그 주제를 고르면
2·3·4단계가 **이미 채워진 채로** 열려 사람은 고르기만 한다.

| 단계 | 미리 만든다 | 걸리는 시간(이 PC 실측) |
|---|---|---|
| 2 훅 문구 | ⭕ 3줄 5 + 2줄 5 | 18초 |
| 3 사진 | ⭕ 인물 5 + 풍경 5 | 한 장 1~4분 → 주제 하나에 20~40분 |
| 4 본문 | ⭕ 10개 | 38초 |
| 5 캐프션 | ❌ 구조상 불가 (아래) | 23초 |

### ⚠ 캐프션은 미리 못 만든다

`make_caption` 은 **확정된 훅과 확정된 본문 10개**를 받아 짓는다
(`backend/app/services/studio_steps.py:334-349` — `CaptionBody(topic, hook, items)`).
사람이 고르기 전에는 재료가 없으니 지금처럼 그 자리에서 짓는다. 23초다.

### ⚠ 미리 만들면 사진·본문이 **확정 훅을 못 본다**

지금은 사진도 본문도 **고른 훅을 받아** 짓는다
(`_do_images` 는 topic + hook_lines, `make_body` 는 `BodyBody(topic, hook)` — `studio_steps.py:313-325`).
훅을 고르기 전에 미리 만들면 그 입력이 없다. 훅 후보 10개마다 따로 만들면 10배라 현실적이지 않다.

→ **주제만 보고 짓는다**(`hook=""`)로 간다. 대가는 문구·그림이 훅과 댜 맞물린다는 것이고,
이건 사람이 편집기·재생성으로 메꾸는 쪽을 택한 것이다. 다른 방법을 찾으면 알려 달라.

### 서버에 필요한 것

- **미리 만든 것을 담을 자리가 없다.** 보관함은 지금 `상황별일본어_보관함.md` 에
  **주제 문자열 한 줄**씩만 적는다(`studio_steps.py:98-121`). 훅·10장 사진 URL·본문 10개를
  넣을 곳이 없으니 서버 저장소가 필요하다. 보관함 md 는 지금처럼 사람이 읽는 목록으로 남긴다.
- **일꾼 순서** — 미리 만들기는 사람이 지금 기다리는 일보다 **뒤에** 둔다.
  지금 일꾼은 `pending` 을 5초마다 보며 한 번에 하나씩 처리한다(`studio_worker.py`).
  미리 만들기가 사진 10장을 잡고 있으면 사람이 누른 단계가 뒤에 밀리는 일이 없어야 한다.
- **상태 표시** — 보관 줄마다 「준비됨 / 만드는 중(몇 장까지) / 실패」를 보여 준다.
  준비된 것을 고르면 기다림 0, 아직이면 지금처럼 진행 표시를 보며 기다린다.
- **버릴 때** — 보관을 푸거나 그 주제로 캐러셀을 만들어 이력에 오르면 미리 만든 것도 같이 버린다.
- **지침서가 바뀌면** 미리 만든 문구는 옛 규칙의 결과다. 줄마다 [다시 만들기] 를 둔다.

### 알고 쓸 것

보관 주제가 쌀이면 이 PC 가 그만큼 오래 그림을 그린다(주제 3개 ≈ 1~2시간).
도중에 PC 가 꾸지면 거기서 멈추고, 다음에 켜질 때 못 끝낌 것부터 이어서 한다.

## 추가 요청 — 주제를 직접 적는 입력란 (2026-09-03)

### 바라는 모습

- **[이 주제로 시작]** — 그 자리에서 주제로 확정하고 2단계(훅)로 내려간다.

  나중에 고를 때 훅·사진·본문이 이미 차 있다.
- 빈 칸이면 버튼은 꾸진 채로 둔다.

### 이력과의 관계

사람이 직접 적은 주제가 [제작 이력](상황별일본어_이력.md) 에 이미 있으면
**막지 말고 알려만 준다** — 「이미 만든 주제예요 (날짜 · 캐러셀 id)」.
이력은 후보를 뽑을 때 중복을 피하려고 있는 것이지, 사람이 일부러 같은 주제를 다시 만드는 것까지
막는 자리는 아니다. 만들면 6단계에서 지금처럼 이력에 한 줄 붙는다.
